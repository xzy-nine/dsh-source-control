# 性能与缓存

本文是刷新触发、取数缓存与首屏耗时的参考页。代码位置见[代码结构](代码结构.md)。

## 刷新与触发

自动刷新以事件驱动为主，另有低频兜底轮询：

| 机制 | 触发源 | 周期/延迟 | 开关 |
|---|---|---|---|
| 自动刷新（事件） | 当前会话事件窗口里已落地的写入/编辑，且目标在所选仓库内 | 5s 冷却 | `autoRefresh`（默认开） |
| 自动刷新（宿主事件） | 宿主事件流里的仓库写操作，且目标与所选仓库同一 | 5s 冷却 | `autoRefresh`（默认开） |
| 自动刷新（兜底） | 定时轮询工作区签名 | 可见 10s / 不可见 120s，快档一次、慢档连续两次同一签名才重载 | 跟随 `autoRefresh` |
| 自动抓取 | 定时循环 | `autoFetchPeriod` 秒（默认 180） | `autoFetch`（默认开） |
| 缓存清理 | 定时循环 | 300s | 无 |

兜底轮询覆盖事件窗口之外的外部写入（编辑器、终端、其它进程），页签可见时按 10s 的快档跑，不可见时退回 120s 的慢档；页签不可见、上一次未结束、面板正忙时跳过。

后台刷新结束时按「工作区条目数 / 已加载提交数」的变化给一条信息类轻量提示（`toast.ts` 的 `info` 类别），只报变化量、不报总数。基线把取数范围（仓库、引用起点、提交窗口与影响提交行的设置项，`use-graph-data.ts` 的 `graphScope`）与「两轮都已就绪」一并记入，范围不同或加载中的轮次只重建基线不提示——否则换仓库、换筛选或加载更多会把两份不同批次的提交数误报成「提交图 ±全部提交数」。

对账与轮询补取按已加载的日志记录数请求窗口（`reconcileWindow`，入参是宿主给出的 `nextSkip`），后台刷新不会把触底加载过的分页收回去。窗口大小不进「按列表长度推导」这条路：列表里还插着贮藏行与未提交伪提交行，按长度算会让窗口逐轮变化，而窗口大小是宿主提交图窗口缓存键的一部分。

错误类提示显示期间到来的信息类提示直接丢弃：失败原因（如 git 钩子未通过）只有这一次，不能被后台刷新的结果告知盖掉。停留时长按类别与文本长度推算（`HOLD_OF`：错误 8–20 秒，信息 3–8 秒）。

## 事件流

宿主事件流（`GET /dsh-source-control/gg/events`，`text/event-stream`）补上事件窗口之外的另一半：执行层在每次非只读写命令结束后推一条 `repository-write`（只带仓库路径，判据是命令跑完，含以非零退出但已改动仓库的冲突合并、拣选冲突与变基停下），因此别的会话、别的工作区与外部进程造成的改动也能即时反映。客户端 `api/repo-events.ts` 解析帧、按退避重连，`use-repository-write-events.ts` 按仓库路径过滤后重载。

同一通道还推 `repository-tree`：`repo-watcher.ts` 分两层监视。**仓库级**看各仓库 git 公共目录的 `worktrees` 与 `modules` 两个名字、仓库根的 `.gitmodules`、以及各已声明子模块目录的出现，监视按 git 公共目录去重，主工作树、链接工作树与子模块共用一套句柄，事件合并窗口 250ms。**工作区级**递归监视工作区根，只判定「仓库集合是否可能已变」：新建的仓库与工作树此前没有句柄，只能由这一层发现；事件合并窗口 400ms，判定见下。工作树与子模块的增删不一定经过执行层（宿主自己的工作树工具、外部命令、编辑器都会改），写事件覆盖不到，因此需要这两层。结构事件到达时宿主先作废发现缓存再广播，客户端按工作区根过滤后调用 `refreshTree()`（不清空已显示的树）。

工作区级判定是纯函数 `isRepositorySetChange`，三类信号：名字里有 `.git` 段时取其所属仓库根，根未知才算变化（已知仓库内部的 `.git` 写操作由仓库级监视负责，否则会形成「事件 → 重新发现 → 读 `.git` → 事件」的死循环）；名字是普通路径且事件为 `rename` 时，该路径自身或下探两层内出现或消失了仓库，或该路径是已知仓库及其祖先；名字缺失时核对已知仓库是否仍存在 —— Windows 的递归句柄删除目录树时只报不带名字的 `change`，这是仓库被整个删除的唯一信号。已知仓库消失时即从集合中移除，因此同一路径只触发一次变化。

仓库级监视的目标**不含** `.git` 与 `worktrees`/`modules` 目录自身。名字缺失的仓库级事件不直接当作结构变化：Windows 上普通 `git status` 也会在公共目录产生一条，直接重扫会让面板反复刷新。此时按 `structureState` 读一次结构状态（各监视目标下被监视名字的存在形态）并与上次比对，未变即忽略；首次比对因没有基线而按变化处理。

两处**不得**纳入监视目标：

- `worktrees` 与 `modules` 目录自身：Windows 上句柄在目录被删除后持续报错，且一次工作树操作触发数万次事件。
- 仓库根的 `.git`：`.git` 内部每次写操作都会以 `.git` 名字冒泡到父目录，一轮 `status` / `add` / `commit` 实测数十次。监视它会形成「事件 → 重取 → git → 事件」的死循环，表现为页面反复刷新。结构变化已由公共目录上的 `worktrees` / `modules` 名字事件覆盖，`.gitmodules` 在普通 git 操作中不产生事件。

结构事件的重取走 `repo-preload.ts` 的 `refreshWorkspace`（保留 `baseNodes`，只作废补齐记录；不受 30 秒重取冷却约束，取数进行期间的连续请求合并为一次后续重取），不走 `dropWorkspace`：后者会发布空树，连续事件会让仓库区反复闪回占位。

一次重载向宿主发两次请求，两路并行：`loadCommits`（提交图窗口；仅首次进入时同时带回仓库信息、引用集合与贮藏）与 `loadWorkingTreeSnapshot`（工作区条目 + 分支 / 上游 / 领先落后）。宿主侧一次提交图请求内部也是并行的：仓库信息、引用集合、贮藏、工作树分支与提交日志互不依赖，同批发出；引用集合透传给提交图，不重复读；首屏下引用集合与分支列表由**同一次** `for-each-ref` 产出（`REF_BRANCH_FORMAT` 与 `parseRefsAndBranches`，同时取 `%(HEAD)`、`%(refname:short)`、`%(symref)` 与引用字段），因此不为此多起子进程。提交图窗口缓存只在宿主（`source-control/host-cache.ts`），客户端不自建一份：键为「仓库 + HEAD + 全部取数参数」，命中即最近使用，按容量淘汰最久未用的一项，写操作与 `invalidateCache` 按仓库（含祖先与后代）作废。客户端只保留渲染态（`lastPanelState` / `lastMaxCommits`）供重新挂载时首帧呈现。

## 刷新耗时

一次 git 子进程的固定开销约 80ms，因此刷新路径的耗时几乎只由「起了几个 git 子进程」决定。七处对策：

| 对策 | 说明 |
|---|---|
| 图形区不等工作区 | `getCommits` 不读 `git status`：未提交伪提交行需要工作区条目数，宿主为它读一次工作区会让提交图的返回时刻取决于工作区读取（`git status` 是两者中最慢的一条），文件越多越慢。该行改由客户端按**同一轮**的工作区快照补出（`commit-diff.ts` 的 `withUncommittedCount`），`assembleCommits` 因此不接收未提交变更数 |
| 引用只枚举一次 | 引用集合与分支列表读的是同一批引用：首屏由一次 `for-each-ref` 同时产出（`REF_BRANCH_FORMAT` 与 `parseRefsAndBranches`，`getRefsAndBranches`），提交图的引用标记不来自这次枚举（见下一行）；`HEAD` 由 `HEAD` 文件解析（`worktree-branches.ts` 的 `readHeadRef`），不起 `git rev-parse` |
| 引用标注并入日志 | `LOG_FORMAT` 末位是 `%D`、`getLog` 传 `--decorate=full`；`parseDecorations` 把装饰解析成 heads / tags / remotes，`refsFromDecorations` 组装成 `RefData` 交给 `assembleCommits`。刷新路径因此不再跑 `for-each-ref`（首屏的仓库信息批仍要一次，用于分支列表）。`CommitTag.annotated` 恒为 false —— 装饰无法区分附注标签，客户端只在 `commitsEqual` 里读它 |
| 仓库事实缓存 | `repo-facts.ts`：`repoLayout` 缓存 git 目录与公共目录（10s、容量 64，写命令按仓库含祖先与后代作废），`readPackedRef` 把 `packed-refs` 解成表（容量 8，按 `mtimeMs + size` 守卫）。`HEAD` 不缓存 —— 它是各缓存键的失效判据 |
| 仓库信息只取一次 | `loadCommits` 的仓库信息批由入参 `withRepoInfo` 显式控制（默认 false），与「是否首屏」解耦；`use-graph-data.ts` 只在某仓库首次取数时传 true，之后复用已知的 remotes/stashes/branch（`panel/graph-window-cache.ts` 的模块级 `knownRepoInfo`，按仓库归一化键，写操作与换仓库时作废） |
| 纯工作区操作不重取提交图 | `panel/index.ts` 的 `run` 第五个参数 `historyChanged`（缺省 true = 全量对账）；暂存 / 取消暂存 / 丢弃 / 忽略规则标 false，改走 `refreshEntries()`，只取工作区快照且不作废窗口缓存。`use-file-change-refresh.ts` 触发的刷新同样走 `refreshEntries()`：写入与编辑不移动 HEAD |
| 数据未变不重渲染 | `panel/commit-diff.ts` 的 `commitsEqual` / `commitsListEqual` / `remotesListEqual` / `entriesEqual`；`reconcile` 路径下数据未变时保持数组引用不变，图形区的泳道布局与更改区的树计算因此不重算（`full` 不短路，主动刷新必须真正重建） |
| 上限按树不按行 | 条目与改动文件的条数上限（`STATUS_LIMIT` 10000、`DETAIL_FILE_LIMIT` 1000）一律经 `source-control/depth-limit.ts` 的 `pickByDepth`：深度小于阈值的整层保留，阈值深度按父目录成组保留（一组放不下就整组不留），仓库根下的条目名额有剩时按顺序补满。解析因此先收全记录再按深度取，不边读边截 |

未提交伪提交行的父提交必须已在提交列表中：提交列表与工作区快照可能读自不同时刻，HEAD 已被别的进程移动时该行会指向一个不在列表里的哈希，泳道图在该处断线。判据是 `commit-diff.ts` 的 `uncommittedParentOf`，`refresh` 与 `refreshEntries` 两处补出该行时共用它。

`refreshEntries()` 只中止**上一次快照**请求（独立的 `entriesControllerRef`），不触碰在途的提交图请求：`phase` 只由 `refresh` 写入，作废在途的提交图会让图形区永久停在 loading。它按条目数就地修正未提交伪提交行（`withUncommittedCount`，含条目数由零变正时补出该行），文案与客户端同格式。

度量：`scripts/bench-git-info.mjs`（取数：每场景的 ms / git 子进程数 / 文件系统次数 / 命令明细，末段对照计划第 1 节的判定标准）、`bench-refresh.mjs`（刷新路径，含 `withRepoInfo` 两种模式对照）、`bench-first-paint.mjs`（首屏）、`bench-ui.mjs`（显示到界面：变更树、提交合并复用率、行文本与标记的冷态与命中态）、`bench-layout.mjs`（泳道布局纯计算）、`bench-discovery.mjs`、`bench-enrich.mjs`、`bench-verify.mjs`。`runGit` 对只读命令有 200ms 结果缓存，采样间隔须大于该 TTL，否则读数偏小且不可复现。

## 仓库树取数

仓库树的取数不在面板重载的两路请求里：客户端插件激活后按**主视图当前会话**的工作区后台预加载（`panel/repo-preload.ts` 的 `activeWorkspaceOf`，判据是会话行的 `retainedBy.mainView`），只取这一个工作区，不遍历会话列表里的其它工作区。一个工作区依次做浅层发现、位置纠正、补齐工作树与子模块、读取领先/落后，每步完成即发布快照；`use-repos.ts` 只订阅快照并维护选中与展开。

补齐按 `ENRICH_BATCH_SIZE`（8）分批下发，每批完成即发布一次快照；领先/落后由 `loadReposSync` 一次取回，宿主对每个仓库调一次 `git for-each-ref --format=… refs/heads`（`BRANCH_SYNC_FORMAT` 与 `parseBranchSync`，`%(HEAD)` 标出当前分支）；无提交的仓库回退一次 `symbolic-ref --short -q HEAD`，此时只给出分支名、上游为空、领先/落后为 0。单个仓库失败以空值兜底，`path` 原样回显入参。

仓库发现逐层并行，结果进 60 秒 TTL 的内存缓存（容量 16，超出按插入序淘汰），仓库写命令结束后按仓库（含祖先与后代）作废受影响的条目（`invalidateDiscoveryCacheFor`）；宿主 `apply()` 注册路由后按已持久化的工作区根启动一次预扫（`primeCachedWorkspaces`），只走按已知仓库位置取树的快路径，失败静默。

## 取数与缓存

「请求 → 数据到手」这一段按四层缓存，有效期与失效判据按各自数据的变化频率定：

| 层 | 落点 | 键 | 有效期 / 容量 | 作废 |
|---|---|---|---|---|
| 进程级事实 | `repo-facts.ts` 的 `layouts` / `packedRefs` | 规范化仓库路径（分隔符统一为 `/`）/ 规范化公共目录 | 布局 10s、容量 64；打包引用无 TTL，按 `mtimeMs + size` 守卫、容量 8 | 写命令结束按仓库（含祖先与后代）作废布局；打包引用由守卫自校验 |
| 子进程结果 | `git-exec.ts` 的 `resultCache` / `inFlightGit` | 仓库 + `JSON.stringify(args)` | 200ms / 64；在途条目收尾即删 | 写命令按仓库（含祖先与后代） |
| 宿主响应 | `host-cache.ts` 的 `graphs` / `repoInfos` / `snapshots` / `hooksPaths` | 仓库 + 取数参数（图窗口另含 HEAD 与贮藏 / 远程标识）/ 仓库 | 30s / 60s / 500ms / 60s，容量 64 / 32 / 32 / 32 | 写命令按仓库作废（`invalidateOnWrite`：含祖先与后代，以及按 `noteRepoCommonDir` 登记的共享 git 公共目录的其它工作树）；`invalidateCache` 同范围 |
| 客户端取数参数 | `panel/graph-window-cache.ts` 的 `knownRepoInfo` / `lastPanelState` / `lastMaxCommits` | 归一化仓库路径 | 模块级，容量 8 | 写操作与换仓库（`dropGraphWindows`） |

`runGit` 的在途复用只对**确认只读**的命令生效（`isReadOnly` 的形态清单）：`status`、`diff`、`ls-files` 的输出随工作区与索引当前内容变化，因此不进 200ms 结果缓存，但仍与在途调用共享同一个子进程 —— 客户端中止后重发、刷新与只取快照并发时因此只跑一次 git。写命令一律独立执行，并发两次写命令仍起两个进程。子进程环境按「只读形态 + 父进程的语言取值」缓存，父进程改语言即重建。

仓库树的批量领先/落后取数是唯一入队的取数：`repo-sync.ts` 的 `loadReposSync` 走模块级 `createLimiter(SYNC_CONCURRENCY)`（`child-process.ts`，上限 5），一次下发全部路径时同时在跑的 git 不超过 5 个；面板的单仓库命令不入队，与「宿主不串行化命令」一致。

引用筛选在取数端生效：`loadCommits` 的 `branches` 由筛选状态决定，「全部」传 null（宿主按 `--branches` 等枚举）、「自动」传当前分支 + 上游 + 分叉来源、「手选」传所选引用短名；窗口缓存键本就含 `branches`，切换筛选即换一个窗口。自动模式的分叉来源由 `loadBranchBase` 取（配置 → 分支 reflog 创建来源 → 默认远程分支，取值顺序同 VS Code 图形视图的 base 引用），只在换仓库或换分支时读；弹窗的引用列表由 `loadRefs` 取，只在打开弹窗或手选校验时读，刷新路径不为它起子进程。

客户端只记「已知远程与贮藏」是否可信：`GraphData.infoKnown` 为真才记为已知值 —— 空远程与空贮藏同样是事实，记下它们才不会让下一次刷新再取一次仓库信息；读取失败不回记，避免把失败固化。`loadCommits` 响应另带 `branch`（当前分支名，取自同一次 `HEAD` 读取），刷新路径因此仍能标出当前分支；`refresh` 的 `selectedId` 走 ref，同仓库内改选不触发取数。

## 首屏空白

一次 git 子进程的固定开销约 80ms（本机实测），因此首屏关键路径上的 git 调用数是空白时间的主因。

三处各自的最短路径：

| 区域 | 关键路径 | 空白来源 |
|---|---|---|
| 仓库列表 | `discoverWorkspace(root, { shallow: true })`：宿主按持久化位置取树，每仓库一次 `stat` + 读 `HEAD`，不起 git | 无位置缓存时退回完整扫描（8 仓库约 260ms） |
| 更改区 | `loadWorkingTreeSnapshot`：一次 `git status --porcelain=v2 --branch -z -uall` | 单次 status 约 90ms |
| 图形区 | `loadCommits` 首屏：仓库信息 / 引用集合 / 贮藏 / 工作树分支同批并行，再与 `git log` 并行 | 最慢一路约 110ms |

仓库列表先出**浅层树**（顶层仓库节点，`children` 全空），工作树与子模块随后补齐：预加载在 `repo-preload.ts` 里按仓库路径把补齐结果存进 `childrenByPath`，`repo-tree.ts` 的 `attachChildren` 负责挂回。判据是「有没有补齐记录」而不是「当前有没有 children」，`rescan()` 丢弃整个预加载状态，因此重扫能反映工作树的增删。浅层树里没有工作树与子模块节点，持久化选中的若正是这类节点，`planSelection` 把它记为待认领、补齐后由 `claimPendingSelection` 认领回原节点；用户手动选中即作废待认领项。

补齐的占用登记与结局处理是两个纯模块：`enrich-claims.ts` 的 `createEnrichClaims()` 记在途与已完成，`enrich-run.ts` 的 `runEnrichBatch()` 按结局决定保留还是释放占用。取消、空结果与失败都必须释放，否则该路径此后既不下发、也不在已完成集合里，工作树永久不出现。空结果与失败还会驱动重试，但按路径累计连续失败次数（`ENRICH_FAILURE_LIMIT`，默认 5）——到上限即按「没有工作树与子模块」处理，不再重试，避免宿主判据与发现层不一致时形成无休止请求；成功一次即清零计数，`rescan()` 的 `clear()` 亦然。

`core.hooksPath` 由 `host-cache.ts` 的 `readHooksPath` / `writeHooksPath` 缓存 60s（钩子文件是否存在仍现读，增删钩子文件立刻可见），`hooksState` 因此在同一仓库反复切换时只起一次 `git config`；该取值由外部进程改动不产生写事件，按仓库作废走 `invalidateCache`。仓库树的领先/落后取数受上限 5 的限流约束（见「取数与缓存」），仓库数不超过 5 时不受影响。

`enrichRepositories` 对「无链接工作树且无 `.gitmodules`」的仓库零 git 调用（`linkedWorktreePresence` + `.gitmodules` 存在性判定，且要求 `.git` 为目录），有来源时才枚举。仓库判据与发现层对齐：`.git` 为目录或文件都算仓库（`hasGitEntry`），`headOf` 经 `worktree-branches.ts` 的 `gitDirAt` 定位 `HEAD`，因此链接工作树与子模块也能解析出分支。`branchesOfOtherWorktrees` 先做无链接工作树判定，为空时直接返回空集。`getStashes` 先看 `<commondir>/logs/refs/stash` 是否存在，不存在时不调用 git。`getRepoInfo` 的远程名由 config 派生（`remote.<name>.<任意子键>`），集合为空才回退 `git remote`。

`scripts/bench-first-paint.mjs`、`bench-discovery.mjs`、`bench-enrich.mjs`、`bench-verify.mjs` 度量这几处；`runGit` 对只读命令有 200ms 结果缓存，采样间隔须大于该 TTL，否则读数偏小且不可复现。

`change-events.ts` 是判据的纯函数层（无导入，可直接单测）：`settledFileChanges` 把事件折成「拿到结果且结果非错误」的写入/编辑，`repositoryRelativePath` 判定模型给出的路径是否真在仓库内。事件窗口是客户端会话事件源，因此 `run_code` 里的嵌套调用按 `tool/ptc-dispatch-start` + `tool/ptc-dispatch` 一并覆盖。

`use-file-change-refresh.ts` 订阅事件源：窗口没聚焦、面板正忙时挂起，连续变更按冷却节流。`use-auto-fetch.ts` 是唯一的定时网络操作，按「聚焦 + 空闲」门控。`use-cache-cleanup.ts` 丢弃过期的悬停统计与完整提交信息缓存。以上 hook 与 `use-graph-polling.ts` 的兜底轮询都从该 hook 暴露的 `busyRef` 读进行中的操作记录，只有**目标仓库**在忙时才挂起。
