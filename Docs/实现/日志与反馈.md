# 日志与反馈

本文是文本日志、耗时汇总与反馈提交的参考页。功能入口见[功能说明](../功能/功能说明.md)。

## 目录与命名

| 层级 | 名称 | 说明 |
|---|---|---|
| 根目录 | `$DSH_HOME/dsh-source-control/logs/` | 与插件状态文档同级；`DSH_SOURCE_CONTROL_HOME` 可改根目录 |
| 反馈暂存 | `outbox/` | 压缩包与正文草稿，启动时整目录清空 |
| 日文件夹 | `YYYY-MM-DD` | 按本地日期归档 |
| 日志文件 | `YYYYMMDD-HHmmss.log` | 每次启动一个文件；文件名升序即启动先后 |

## 模块划分

日志模块三件：`log-format.ts` 只做格式（logcat threadtime：`MM-DD HH:MM:SS.mmm  PID  TID LEVEL TAG: message`，含换行的消息逐行写出）；`log-retention.ts` 只做命名与淘汰判据（纯函数）；`logger.ts` 负责落盘与清理。

root 与 `state-store.ts` 同序解析；同一秒内多次启动追加进同一份文件。

写入策略：行先入缓冲，`FLUSH_DELAY_MS`（250ms）合并为一次追加写，缓冲到 512 行立即落盘，`process.on('exit')` 同步收尾。定时器 `unref()`；写盘失败静默。

## 耗时汇总

耗时汇总（`api/cost.ts`）：单条命令不记日志，按「一次刷新」把墙钟、命令耗时合计、子进程数与各命令明细汇总成一行 `perf` 记录。

分组按客户端随请求带来的 `refreshId`（`panel/graph-window-cache.ts` 的 `nextRefreshId`，带随机会话前缀以免多面板撞号），无编号的命令按仓库与空闲窗口（3 秒）归组；**只按空闲定时器冲刷**，不因同一仓库出现新编号提前写出 —— 一轮里的提交图与工作区快照并行发出、下一轮可能在上一轮收尾前就开始，编号交错到达会让每条汇总只剩部分命令。墙钟取「首条命令开始 → 末条命令结束」（不含命令之间的空闲）。

子进程数按「命令自己的轮次登记」统计：`routes.ts` 为每条命令建一个 `api/refresh-scope.ts` 的登记并用 `runInRefreshScope` 包住处理体，`spawnGit` 每启动一个子进程就把当前登记的计数加一，汇总累加该轮各命令的计数。按仓库取计数器再算差值不成立：并发轮次的时间窗重叠时会互相把对方的子进程算进来，而单命令轮次在收尾后才取基线，差值恒为零。

## 清理

`initLog()` 调 `cleanLogs()`。保留期按日文件夹名比字符串（`planExpiredDayFolders`，当天算第一天）；体积按 `planDayEvictions` 从最新文件向前累计到 `DAY_FOLDER_LIMIT_BYTES`（15 MB）；**正在写入的那一份由 `keep` 排除**，不参与累计也不会被删。

`cleanLogs()` 同时清空 `outbox/`：目录里只有一次性的取用物（待拖进评论框的压缩包、已由 `gh` 写进 issue 的正文草稿），母本日志在日文件夹里不受影响，清空后仍能重新打包。清理只在启动时做一次，会话中的压缩包一份不删——用户可能还没上传。

## 反馈

`feedback.ts` 是提交编排（取日志 → 脱敏 → 打包 → `gh issue create --body-file` → 回投 issue 地址），`feedback-text.ts` 拼正文（纯函数），`log-archive.ts` 用系统 `tar -a -cf` 打包（不可用时退回未压缩副本），`log-redact.ts` 脱敏（纯函数）。

脱敏只在提交反馈时生效，原始日志保持原样。正文走 `--body-file`：长描述会让命令行参数超出系统上限。

反馈入口有两处，打开同一个页签：设置面板的「反馈」页签，与存储库区标题行里克隆和设置按钮之间的反馈按钮。

字段：类型（缺陷 / 建议 / 其它，写进 issue 标题前缀）、标题、描述。勾选「附带日志文件」后，宿主取当前启动的日志、按需脱敏、压成 zip，放在日志根目录的 `outbox/` 下。点「提交反馈」由宿主执行 `gh issue create --repo xzy-nine/dsh-source-control --title … --body-file …`。

提交成功后的去向都由结果弹窗承接：issue 地址与压缩包位置各是一个可点入口，正文另带「自动打开路径与反馈页便于提交」（默认勾选），勾选状态下关闭弹窗才先定位压缩包、等宿主受理后再打开 issue 页。表单页只留输入与提交按钮。

脱敏（默认开启，可勾选「停用脱敏」）：

| 内容 | 占位符 |
|---|---|
| URL 里的账号口令 | `<url-credential>` |
| 令牌串（`ghp_` / `github_pat_` / `sk-` / `xox[baprs]-` / `Bearer`） | `<token>` |
| 系统用户名（独立出现时） | `<user>` |

本地路径不处理：排查问题需要看清文件位置。「豁免字符串」按行登记原样保留的内容，登记后不再替换。

未安装 `gh`、未登录、缺 scope 或没有该仓库的 issue 权限时，弹窗给出处理建议与日志目录，由用户自行补齐，或到上游仓库手动创建 issue 并上传压缩包。

日志不交给 `gh issue create --attach`：user-attachments 端点只接受图片与视频的 content type，文本与压缩包一律被 `content_type` 校验拒绝（`.log`/`.txt`/`.zip`/`.pdf` 均实测失败）。因此流程是「本地打包 → 建 issue → 提示用户把压缩包拖进评论框」。
