dsh-source-control 插件优化计划（参考 VS Code git 扩展）
目标与成功判据
以 VS Code 内置 git 扩展（E:\GitHubCode\98Ref\03Windows\vscode\extensions\git）为参照， 找出本插件在「变更区 / 提交 / 推送 / 冲突 / 工作树」四个面的能力缺口并补齐。成功判据：

冲突（未合并）条目不再同时出现在「暂存的更改」与「更改」两组，且给出可用的解决动作。
提交支持 --signoff、--allow-empty、-S/--no-gpg-sign（VS Code 的 CommitOptions 全量）。
推送能选择 --force / --force-with-lease（宿主 PushMode 已就绪，客户端从未透传）。
变基停下后可在面板内继续 / 中止，不必切终端。
仓库行可创建链接工作树（VS Code 的 git.worktree add 流程）。
全部改动通过 pnpm lint、pnpm typecheck、pnpm test（含重复代码门禁）。
一、冲突条目分组与解决（最高优先，实测存在缺陷）
现状（已核实）

src/source-control/working-tree.ts:686 的 parseStatusSnapshot 把 v2 的 u（未合并）记录写入 entries，index/worktree 取 XY 两列（如 UU、AA、DU）。
src/client/panel/changes.ts:35 的 changeOf：staged = index !== ' ' && index !== '?' && index !== ''， UU 因此判为已暂存。
src/client/panel/sections.ts:307-309 与 changes.ts:307-309 两个分组的 filter 分别是 index !== ' ' && index !== '?' 与 worktree !== ' '，UU 两条都成立。
实测确认：git restore 对未合并路径直接失败（error: path 'f.txt' is unmerged，退出码 1）， 因此现有「丢弃」对冲突条目必然报错；git checkout --ours/--theirs 才是可用入口。
结论：冲突文件当前会同时列在两组里，且「丢弃」按钮对它们一定失败。

改动

src/client/shared/types.ts：WorkingTreeEntry 增加 unmerged?: boolean。 宿主侧 parseStatusSnapshot 在 kind === 'u' 时置真。
新增纯函数模块 src/client/panel/conflicts.ts：
isUnmerged(entry)：未合并判定（index 或 worktree 属 DD AU UD UA DU AA UU 组合）。
conflictGroupsOf(entries)：拆成 merged / unmerged 两份。
conflictActionOf(entry)：给出可用动作（保留双方 / 取我方 / 取对方 / 标记已解决）。
src/client/panel/changes.ts 的 ChangeGroup：filter 排除未合并条目；新增第三个分组 「合并冲突」（merging 为真且有未合并条目时显示），行内按钮改为冲突解决动作。
src/client/panel/sections.ts：ChangesSection 渲染新分组，传 merging。
宿主新增命令 resolveConflict（git checkout --ours/--theirs <path>）与 markConflictResolved（git add <path>），落在 src/source-control/git-actions.ts， 路由加两条 case，客户端加 src/client/api/conflicts.ts。
提交框在 merging 且仍有未合并条目时禁用提交（当前只判 merging，不判是否还有冲突）。
测试：test/conflict-groups.test.mjs 覆盖分组纯函数（UU 只进冲突组、MM 不进、 混合列表的拆分）；test/status-snapshot.test.mjs 补 u 记录的未合并标记。

二、提交选项对齐 VS Code CommitOptions
现状：commitStaged(repo, message, amend, skipHooks) 只覆盖 -m / --amend / --no-verify / --no-edit。VS Code 另支持 signoff、signCommit、empty、all（git.ts:2118-2175）。

改动

src/source-control/working-tree.ts 的 commitStaged 增加可选参数 { signoff, signCommit, allowEmpty }，按序追加 --signoff / -S | --no-gpg-sign / --allow-empty。
路由 commitStaged case 透传三个布尔。
src/client/api/working-tree.ts 的 commitStaged 同步扩参。
src/client/panel/index.ts 的 submit：从设置读取新选项并传入；runHooks 语义不变。
src/client/panel/settings.ts 与 src/client/shared/types.ts 的 Settings 增加 commitSignOff、commitSign（三态：default / always / never）、commitAllowEmpty， 默认全部关闭，落在「全局设置」页。
测试：test/api-commands.test.mjs 补一条：带 signoff 的 commitStaged 产生含 Signed-off-by 的提交；allowEmpty 在无暂存改动时成功。

三、推送模式（force / force-with-lease）
现状：宿主 PushMode（git-types.ts:20）与 pushBranch(repo, name, remote, setUpstream, mode, skipHooks) 已支持，路由 pushBranch 也读 msg.mode；但客户端 pushBranch（api/remotes.ts:28）与 pushUpstream（:42）都把 mode 写死为空串，界面没有任何选择入口。

改动

src/client/api/remotes.ts：两个函数增加 mode: PushMode = '' 参数并透传。 PushMode 在 src/client/shared/types.ts 声明（与宿主同名同取值）。
src/client/panel/index.ts 的 pushCurrentBranch 增加 mode 入参；handleSync、 handlePublish、仓库行菜单的「推送」在推送前弹出一次模式选择（showSelect： 普通推送 / 强制推送 / 强制带租约推送），force-with-lease 为推荐项。
推送被拒绝且错误文本匹配 non-fast-forward / fetch first 时，提示里直接给出 「可用强制带租约推送重试」的引导（不做自动重试）。
测试：test/api-client.test.mjs 断言 pushBranch / pushUpstream 的 mode 透传； test/api-commands.test.mjs 经真实 handler 断言 --force-with-lease 出现在参数里。

四、变基与拣选停下后的恢复
现状：rebase 只会启动（git-actions.ts:502），cherrypickCommit 同样只启动；冲突停下后 面板只显示「取消合并」（merging 由 MERGE_HEAD 判定，git-query.ts:385）， 没有继续 / 中止变基的入口，用户必须切终端。

改动

宿主新增 rebaseContinue（rebase --continue，配 GIT_EDITOR: true）与 rebaseAbort、cherrypickAbort，落在 git-actions.ts；路由加 case。
仓库状态快照补充两个判定：rebasing（存在 rebase-merge 或 rebase-apply）与 cherryPicking（存在 CHERRY_PICK_HEAD），与 mergeInProgress 同批并行读取 （git-query.ts 的 getWorkingTreeSnapshot）。
WorkingTreeSnapshot 增加 rebasing / cherryPicking；客户端类型同步。
src/client/panel/sections.ts 的提交框动作区：按状态显示「继续变基」「中止变基」 「继续拣选」「中止拣选」，与既有「取消合并」同一组、同一禁用规则。
提交框提示文案按状态切换（当前只有 merging 一条）。
测试：test/snapshot.test.mjs 补三种进行中状态的快照契约；test/submit-state.test.mjs 补「变基进行中主按钮固定为提交 / 继续」。

五、链接工作树创建
现状：插件能发现、枚举与移除工作树（repo-discovery.ts、working-tree.ts:1070）， 但不能创建。VS Code 有完整流程（commands.ts:3538 起：选起点 → 命名 → 选路径 → worktree add）。

改动

宿主新增 addWorktree(repo, path, commitish, branch?)（git-actions.ts）， 路径限定在仓库父目录或仓库同级目录之下，拒绝绝对路径越界与已存在路径。
路由加 case；客户端加 src/client/api/worktrees.ts。
仓库行右键菜单（panel/index.ts:1359 的 handleRepoMoreActions）新增「新建工作树…」： 表单三步（起点分支/提交、新分支名或直接分离、目标路径，默认 <仓库父目录>/<仓库名>.worktrees/<分支名>），与克隆一样经 showForm。
创建成功后 rescan()，与移除工作树同一套收尾。
忙碌记 history 影响面。
测试：test/api-commands.test.mjs 经真实 handler 断言 worktree add 参数与越界拒绝； 仓库树发现已有用例覆盖新增节点挂载。

七、明确不做
交互式变基（rebase -i）：需要编辑器交互，宿主已显式拒绝，保持现状。
行级 / hunk 级暂存（VS Code 的 staging.ts）：需要编辑器选区联动，超出侧栏面板形态。
blame / 时间线 / quick diff：依赖编辑器装饰与文件系统提供者，DSH 无对应 API。
askpass 集成与凭据弹窗：插件已统一 GIT_TERMINAL_PROMPT=0，凭据交给终端。
分支保护、随机分支名、emoji 渲染：属于 VS Code 工作区配置生态，DSH 无对应概念。
实施顺序与验证
第一组（冲突分组与解决）、提交选项、推送模式三者互不依赖，可并行开发。
恢复入口（依赖快照新字段）、工作树创建随后。
第六组小项按依赖穿插。
每组完成后各自跑 pnpm lint && pnpm typecheck && pnpm test；全完成后跑 pnpm check:duplication 与 scripts/bench-refresh.mjs、bench-first-paint.mjs 确认首屏与刷新耗时无回归。文档更新：doc/功能说明.md 缺文件时新建，并在 README.md 的功能列表补一行；提交信息只写说明性描述。
