# 「数据 → 界面」性能与缓存优化计划

## 1. 目标与判定标准

目标：把「宿主数据已到手 → 界面呈现」这一段做成**每帧只做必要工作、派生值只算一次、缓存有容量上限**，不改变任何可见行为、不改宿主协议与持久化结构。

判定标准（可核对）：

1. 在提交信息框里连续输入，提交图行与变更树不参与重渲染（只有提交框与标题栏重渲染）。
2. 滚动提交图时，状态更新按帧合并，且只在「可视窗口的起始行下标」变化时才重渲染（不再每个 scroll 事件一次）。
3. 悬停一行取回统计后，只有该行的浮窗数据变化，其窗口内其余行不重渲染。
4. 悬停/翻译/译文三份缓存有容量上限，长会话不再无限增长（现有仅按 TTL 清理）。
5. 暂存一个文件后，未变化的条目与提交对象保持引用不变，未变化的行不重渲染。
6. `pnpm lint` / `pnpm typecheck` / `pnpm test` 全绿；`check:duplication` 不新增克隆（基线不动）；`pnpm build` 客户端产物增量 < 2 KB。
7. 新增 `scripts/bench-ui.mjs` 可复现地量化这几步（含缓存命中与提交对象复用率）。

## 2. 现状与本机实测

渲染链路：`use-graph-data.ts`（取数 + 对账，已按 `commitsEqual`/`entriesEqual` 保留引用）→ `panel/index.ts`（`PanelState` 与全部派生 memo）→ `sections.ts` 三个分区 → `graph/index.ts`（窗口化提交行 + 泳道 SVG）、`changes.ts`（变更树）、`repo-row.ts`（仓库行）。

已有的好东西（保留不动）：宿主缓存与窗口缓存、提交列表/条目/远程的逐字段相等判定、图形区窗口化渲染（`OVERSCAN_ROWS`）、滚动期间推迟悬停取数（`SCROLL_SETTLE_MS`）、同色直线合并成一个 `<path>`、`layoutCommits` 与 `offsets/range/visibleCommits` 的 memo。

本机实测（Node 24，`node --input-type=module` 直接跑 src 里的纯函数）：

| 纯计算 | 200 | 1000 | 4000 |
|---|---|---|---|
| `changeRowsOf`（变更树） | 0.21 ms | 0.38 ms | 1.94 ms |
| `layoutCommits`（泳道布局） | 0.16 ms | 0.48 ms | 2.15 ms |
| 40 行派生标记（`refLabels` 形态 + 未提交文案正则） | — | — | ≈0.0 ms/次 |

结论：**纯计算不是瓶颈**。瓶颈是「重渲染放大」：

1. `graph/index.ts:664` 的 `scrollTop` 是 state，每个 scroll 事件都 `setScrollTop`（`handleScroll` 无节流）→ 整棵 `CommitGraph` 重渲染（22px 行高 + 约 320px 视口 + 12 行 overscan ⇒ 常驻约 40 行 DOM），每行重建元素、重算 `refLabels`/`displayMessage`/`segmentGeometry`。
2. 客户端**没有任何** `React.memo`；`panel/index.ts` 任一状态变化（输入提交信息、悬停写缓存、忙碌标志、30 秒时钟 `refreshClock`）都会重渲染仓库区 + 变更区 + 图形区。
3. 逐行传入的回调每次渲染都是新函数：`graph/index.ts:900-901` 的 `onTranslate`/`onCancelTranslate`、`changes.ts:441` 的 `onToggle`、`sections.ts:534` 的 `onSelect`、`sections.ts:557` 的 `renderDetail`、`panel/index.ts:1701` 的 `issueLinking()`（每次新对象）、`1690/1698` 的内联 `onLoadMore`/`onRefresh`。不先消除这些，加 `memo` 也命中不了。
4. 未 memo 的派生：`changes.ts:307-311`（每次渲染过滤 + 建树 + `countLeaves` 递归）、`panel/index.ts:760` `stagedPaths`（每次渲染 O(条目数)）、`sections.ts:463` `visibleTranslatable`（逐条标题逐字符统计书写系统）、`changes.ts:403` 的 `menu` 对象。
5. 缓存只有 TTL 没有容量：`use-commit-stats.ts:94-98` 的统计/完整信息/译文三份 Map 在保留期内可无限增长，且每次写入都整份复制（`new Map(previous).set(...)`）。
6. 时钟：`panel/index.ts:155-158` 的注释写「只在面板可见时跑」，代码没有可见性判定。

## 4. 实施

### 4.1 新增缓存基元 `src/client/shared/cache.ts`

纯模块，无 React、无其他 import（可直接单测；风格对齐 `shared/text.ts`）。

- `class LruMap<K, V>`：内部用 `Map` 的插入序；`get` 命中即置为最新（delete + set），`peek` 不改变次序，`has`/`delete`/`clear`/`size`/`limit`/`keys()`；`set` 后若 `size > limit` 则淘汰最旧直到 `ceil(limit * ratio)`（`ratio` 默认 0.8，构造参数 `{ limit, ratio? }`）。
- `forObject<K extends object, V>(compute: (key: K) => V): (key: K) => V`：`WeakMap` 缓存，键随对象回收。
- `forKey<K, V>(compute, { limit, ratio? }): (key: K) => V`：`LruMap` 缓存。
- `mapsEqual<K, V>(left, right, equals?)`：先比 `size`，再逐项（默认 `Object.is`）。
- `trimOldest(map: Map<K, V>, limit: number): Map<K, V>`：超限时删最旧的若干个，返回原 Map（供不可变写入路径复用）。

### 4.2 图形区：窗口状态、行模型、memo

### 4.4 数据层：让行级 memo 真的能命中

- `src/client/panel/commit-diff.ts` 新增两个纯函数（与现有 `commitsEqual`/`entriesEqual` 同风格）：
  - `mergeCommits(previous, next): Commit[]`：按哈希建 `Map`，逐项 `commitsEqual` 为真则复用 previous 里的对象，否则用 next 的对象；顺序取 next，**总是返回新数组**（`full` 刷新仍真正重建数组，不短路）。
  - `mergeEntries(previous, next): WorkingTreeEntry[]`：同类，键为 `path`（+ `origPath`），四字段全等才复用。
- `src/client/panel/use-graph-data.ts`：`refresh`（reconcile 与 full 都过 `mergeCommits`/`mergeEntries`；等同判定的短路逻辑保留）、`mergeSnapshot`、`refreshEntries`、`reloadGraphOnly`、`loadMore`（追加页也走 `mergeCommits`，老页对象保持引用）。
- `src/client/panel/use-repos.ts`：`setSyncById(previous => mapsEqual(previous, next, syncEqual) ? previous : next)`，避免每次发布都换 Map 引用。

### 4.5 悬停/翻译缓存加上限

`src/client/panel/use-commit-stats.ts`：

- 常量 `CACHE_LIMIT = 400`；每次写入后 `trimOldest(map, CACHE_LIMIT)`（保留现有 copy-on-write 与 `stamps` TTL 清理，两者正交：超容按插入序淘汰，超时按时间戳淘汰）。
- 三份 Map（`statsByHash`/`messageByHash`/`translatedByHash`+`translatedFromByHash`）同规则；换仓库时照旧整体清空。
- 不做「可变 LRU + 版本号」改造：那会改 `CommitCacheMaps` 契约并波及 6 个组件，收益（复制一份 ≤400 项 Map）远小于风险。

## 6. 边界与失败模式

| 情形 | 处理 |
|---|---|
| `commits`/`entries` 变但多数项未变 | `mergeCommits`/`mergeEntries` 复用未变对象；变化的行照常重渲染 |
| `head` 变化（检出） | `labelsOf` 缓存键含 `head`，自动重算 |
| 贮藏行 / 未提交行 | 文案与标记仍由 `row-model` 的纯函数给出，缓存按 commit 对象身份，文案变化必然伴随新对象 |
| 展开详情改变行高 | `offsets` 变 → 触发 effect 重算 `topIndex`；`visibleRange` 已覆盖非均匀行高 |
| 视口高度 0（首帧未测量） | `visibleRange` 退化为 `first + overscan`，与现状一致 |
| 无 `requestAnimationFrame`（测试/旧环境） | 退回 `setTimeout(0)`；卸载时清掉未执行的回调 |
| 缓存淘汰掉正在展示的行 | 下次悬停重新取数（与现在 TTL 过期一致） |
| 面板不可见 | 时钟停止推进；其余刷新仍照旧（不受影响） |
| 极端条目量（上万变更） | 本计划不做变更树虚拟化：靠「提交框与变更列表拆开 + `memo`」保证只有数据真变时才重建；量级风险写进文档，留作独立议题 |

| 风险 | 控制 |
|---|---|
| `memo` 之后 props 不全导致界面不更新 | 逐个组件核对 props 清单；`CommitGraph`/`ChangeLists` 只接收数据与本模块内 `useCallback`/`useMemo` 出的回调；每一步可单独回退（`memo` 是叠加改动） |
| 窗口状态改造影响触底加载/定位 | `maybeLoadMore` 仍读元素实测值；`goToHead` 的滚动位置由既有 effect 处理；新增 `window-range` 单测 + 手动核对三处（首屏、触底、展开详情后滚动） |
| 身份复用掩盖了真实变化 | 复用判据直接复用现有 `commitsEqual`/`entriesEqual` 字段集；`full` 刷新仍返回新数组 |
| 重复代码门禁 | `LruMap` 只实现一份；`pnpm check:duplication` 必须与基线一致 |
| 客户端体积 | 目标增量 < 2 KB；超出则把 `forKey`/`trimOldest` 收敛为最小实现 |

## 12. 实施顺序（单线程，无子代理）

1. `shared/cache.ts` + `test/cache.test.mjs`
2. `graph/window-range.ts` + `test/window-range.test.mjs`；`graph/index.ts` 改窗口状态
3. `graph/row-model.ts` + `test/row-model.test.mjs`；`graph/index.ts` 接入 + 行组件 `memo`
4. `changes.ts`/`sections.ts`/`change-tree.ts` 的 memo 与拆分（含 `primitives.test.mjs` 顺序约束）
5. `commit-diff.ts` 的 `mergeCommits`/`mergeEntries` + `use-graph-data.ts`/`use-repos.ts` 接入 + 测试
6. `panel/index.ts`（`stagedPaths`、`issueLinking`、内联回调、时钟门控）、`use-commit-stats.ts` 容量、`language.ts` 判定缓存
7. `scripts/bench-ui.mjs` + `AGENTS.md` 文档
8. 全量门禁：`pnpm lint` → `pnpm typecheck` → `pnpm test`（含 `check:duplication` 与 `build`）→ 手动核对 6 条判定标准

## 13. 假设

- React 18 的 `memo`/`useMemo`/`useCallback` 语义可用；客户端仍只用已外部化的 5 个裸模块，不新增 import。
- Node ≥ 22 的类型剥离可直接跑 TS 纯模块（现有 bench 已这样用）。
- 「显示到界面」只指客户端从 `PanelState` 到 DOM 的这一步；取数、git 子进程数与宿主缓存不在本次范围。
