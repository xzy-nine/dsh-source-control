# Agent Note: 仓库树按节点 id 去重与主动重扫入口

Status: implemented

## Problem

子模块改名（`git mv` 移动目录并改写 `.gitmodules`）之后，存储库区会在父仓库下同时画出两行同路径的子模块行，例如 `desktop/winbridge` 出现两次。

同一路径的重复来自三个来源，三者都不需要仓库本身出错：

1. `.gitmodules` 里可以有多个 `[submodule "..."]` 段声明同一个 `path`。改名时只改 `path`、保留旧段名，或手工追加一段，都会留下两个声明。
2. 补齐是按仓库路径分批下发的，每批结果写进 `childrenByPath` 后重建整棵树。两次补齐（初轮与结构事件触发的重取）交叠时，同一路径的 children 可能被写入两次之外的另一条路：节点自带的 children 与补齐记录同时存在时，`attachChildren` 直接采用节点自带的，于是同一批结果里两条记录各画一行。
3. 仓库节点与子模块节点的身份都用路径派生的 id，因此重复行在界面上完全一致：点哪一行、选中哪一行无法区分，而 `expandedIds` / `selectedId` 只记 id，两行共享同一展开与选中状态。

第二个缺口是能力缺失：仓库树只在面板挂载、结构事件与克隆后窗口聚焦时重取。事件漏掉（`ctx.fs.watch` 只观察直接子项，回调不给名字）、或结构变化无法只靠事件补齐时（`.gitmodules` 被编辑、仓库被移动或改过名），用户没有任何入口让面板按磁盘现状重取一次。仓库行的右键「刷新」只重载选中的仓库，不重扫树。

## Decision

去重放在两处，各自负责一层：

- `submodule-parse.ts` 的 `submodulePathsWithin` 按首次出现去重。发现层、补齐层、结构监视与子模块初始化四处共用它，因此同一声明路径只产出一个节点。这一层解决来源 1。
- `repo-tree.ts` 新增 `dedupeNodes`，由 `attachChildren` 在把补齐结果挂回浅层节点之后整体调用，递归进入 children 并按 `id` 保留首次出现。这一层是兜底：无论上游因为什么给出重复节点，渲染前都收敛成一行。内容唯一的节点保持原引用，仓库行按节点对象记忆化，因此去重不引起整体重渲染。

去重按 id 而不是按路径字符串：id 是路径归一化后的结果（Windows 上统一小写、分隔符统一），两个写法不同的同一目录本来就是同一个节点。

主动重扫入口是 `rescanWorkspace(root)`，接在存储库区标题栏的刷新按钮上：

- 与结构事件用的 `refreshWorkspace` 一样不清空已发布的树，取数期间界面继续显示上一轮结果。
- 与它不同的是置 `nextFullScan`，下一轮发现带 `fullScan: true` 下发，绕开持久化的仓库位置做完整扫描。持久化位置只在完整扫描后写回，过期时快路径会一直按旧位置取树，而随后的位置纠正被 10 分钟节流挡住——这正是「面板开着时树一直不对」的成因。
- `discoverWorkspace` 在 `fullScan: true` 时先作废发现缓存。缓存的 TTL 是 60 秒，不作废会让用户主动刷新在 60 秒内返回同一份旧结果。
- 同时作废补齐记录、占用登记与已取过的领先/落后：节点集合可能变，新增节点才有值可取。
- 在途时只登记 `pendingRefresh` 与 `nextFullScan`，由那次取数结束后补做一次，不中止在途请求。
- 快照新增 `refreshing` 字段，标题栏据此给出进行中指示；该字段在 `start` 与取数收尾处发布。

## Alternatives considered

**只在渲染时跳过重复行。** 否决：重复节点仍留在状态里，`findNode` 返回第一个、`flattenVisible` 画出两个，两者对「选中哪一行」给出不同答案；而且去重规则要写进渲染路径，仓库行记忆化也随之失效。

**只在 `submodulePathsWithin` 去重。** 否决：它只覆盖 `.gitmodules` 的重复声明。补齐结果与节点自带 children 并存的那条路仍会给出重复，而那条路的输入来自宿主，客户端无法假定它已去重。

**主动刷新走 `rescan()`（先发布空树再重取）。** 否决：`rescan` 会先把树清成占位，点一次闪一次；结构事件驱动的重取正是为了避免这个才用 `refreshWorkspace`。用户明确要求「按磁盘现状重取」时同理，只是这一次要额外绕开持久化位置。

**给宿主加一条 `rescanForRepos` 命令真的重扫。** 否决：该命令已在 `api/misc.ts` 里作为占位恒回成功，没有任何副作用；真正的重扫发生在客户端预加载模块，加一条命令只是多一层转发。完整扫描由 `discoverRepositories` 的 `fullScan` 参数表达，已存在。

**轮询仓库树以兜住漏掉的事件。** 否决：一次重取包含全目录扫描，轮询会把宿主拖住；用户主动刷新是这类「事件覆盖不到」的缺口更便宜的出口。

## Consequences

**收益**：同路径的子模块只画一行，选中的就是点中的那一行；改名、移动或 `.gitmodules` 编辑之后，用户点一次刷新即可按磁盘现状重建，不必重启 DSH。

**代价**：

- 重复被静默合并：`.gitmodules` 里真有重复声明时，界面只画一行，不提示声明本身需要清理，用户的 `.gitmodules` 仍保持重复状态。
- 主动刷新会做一次完整目录扫描（默认上限 5000 个目录、三层），大工作区上耗时可见，因此只提供手动入口，不接进自动刷新。
- `refreshing` 是快照字段，新增订阅方读取它才能显示指示；不读的订阅方照常工作。

## Testing

- `test/repo/repo-tree.test.mjs`：同一层重复 id 只留首次出现且唯一节点保持原引用；去重递归进入子节点；`attachChildren` 在顶层与子层双重重复时各只留一行。移除 `dedupeNodes` 调用后「合流后的树按 id 去重」用例转红。
- `test/repo/repo-submodule-bound.test.mjs`：`submodulePathsWithin` 对同一路径的多次声明只留首次出现。去掉去重后该断言转红。
- `test/repo/repo-preload.test.mjs`「rescanWorkspace：绕开持久化位置做完整扫描」「在途期间的请求登记为完整扫描」：断言下发的 `discoverRepositories` 带 `fullScan: true`、重取期间不发布空树、`refreshing` 在开始与收尾各自发布、在途请求被补做。把 `nextFullScan` 读成常量 `false` 后两条用例转红。
