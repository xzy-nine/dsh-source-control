# Agent Note: 冲突条目在差异页显示并可就地解决

Status: implemented

## Problem

冲突（未合并）条目在面板里既没有可读的差异，也没有解决入口，用户必须切到终端。实测本机 git 与现有代码，原因是三处叠加：

- 工作区作用域用 `git diff -- <path>`，未合并路径输出 `diff --cc` 与 `@@@ … @@@` 三路 hunk 头，`parseUnifiedDiffHunks` 只认两路 `@@`，解析结果是 0 个 hunk；
- 新旧正文用 `git show :<path>`，未合并路径没有 stage 0，命令以 `path is in the index, but not at stage 0` 失败，两侧都变成 null，文件状态因此被误判成新增；
- `changeOf` 把「索引列非空」判为已暂存，而冲突条目的两列是 `U`/`A`/`D` 的组合，于是 `UU` 同时落进「暂存的更改」与「更改」两组。

另有一条隐含缺陷：丢弃对冲突必然失败，`git restore -- <未合并路径>` 一律回 `path '<p>' is unmerged`。

## Decision

**分组按白名单判定。** 索引列只认 `M`/`A`/`D`/`R`/`C`，工作区列只认 `M`/`D`/`R`/`A`/`T`（与 VS Code git 扩展 `repository.ts` 的 status 分派同一口径）。未合并码不属于任一侧，因此冲突不会重复出现，不必逐条排除。第三组「合并冲突」常驻在前，没有冲突时不渲染。

**冲突种类两端只有一份定义。** `src/shared/conflict-kind.ts` 给出七种 XY 组合、种类名、展示文案与「是否仍有冲突标记」的判据；宿主据此给 `WorkingTreeEntry` 补 `unmerged`，客户端分组、动作可用性与差异页读同一份。宿主与客户端分别打包，因此该模块放进两端都有的 `src/shared/`。

**冲突在差异页用三方合并视图。** 照 VS Code 合并编辑器（`workbench/contrib/mergeEditor`）的路数：不解析工作区里的冲突标记，而是取 `:1:`（基线）、`:2:`（我方）、`:3:`（对方）三份文本，各自与基线算行差异，再把两组差异按基线位置对齐成区间——两侧改到同一处即同一个区间，相隔较远的各自成段。区间与选择表在 `shared/merge-ranges.ts`，`merge-view.ts` 画成左我方、右对方、中间一列覆盖方向：`《` 用对方覆盖我方，`》` 反之以。结果是选择表的纯映射，因此连续取舍不读写文件；点「写回结果」才由 `merge-ops.ts` 算出全文落到工作区，全部冲突处理完后自动标记已解决。

取舍只有两个方向，没有「两边都留」「保留基线」「两边都不要」：这个视图的定位是**看清冲突并给出编辑指导**，不是完整的合并编辑器。并集与丢弃是编辑动作，交给编辑器或后续的写回策略，混进这里会让「按段判断该信谁」这个主任务变模糊。

**行评论并入同一视图。** 差异页原有的行选区与「插进对话输入框」的评论链路复用到这里：每行带该侧行号属性，拖选后浮出评论框，评论按「我方 / 对方第几行」定位。合并视图里两栏是两份不同的内容，行号各按自己那份编号，因此不能套用差异页的新侧 / 旧侧写法。

这样处理的理由是标记不是权威：用户手工改过工作区之后，按标记切分得到的段与真实三方内容已经对不上，而 `:1:`/`:2:`/`:3:` 始终是 git 记录的那三份。

**分段暂存走补丁块。** `hunk-ops.ts` 把文件的补丁按 `@@` 切开，只把选中的块交回 `git apply --cached`（取消暂存加 `-R`）。整文件的 `add` / `restore --staged` 表达不了「同一文件暂存一半」。暂存基于「工作区相对索引」的补丁、取消暂存基于「索引相对 HEAD」的补丁，两者的块号各自独立，因此必须用对应那份补丁来切。

**行尾按文件原有形态还原。** 冲突改写与补丁重放都要写回文本：Windows 上 `core.autocrlf` 让工作区文件是 CRLF，而解析按 `\n` 切分。两处都先剥 `\r` 再按原形态拼回，否则标记行带 `\r` 会让 `$` 锚定的标记正则匹配不到，整份文件被当成没有冲突。

**解决动作分两种粒度。** 行内与右键给「采用我方」「采用对方」「删除文件」「标记为已解决」，另在菜单里给「重新生成冲突标记」。采用一侧落 `git checkout-index -f -u --stage=2|3` 再 `add`：`git checkout --ours` 在该侧缺失时整条命令失败且报错随种类变化，而 `checkout-index` 的失败判据固定。该侧缺失（我方删除取我方）时不做无意义复制，改为把对方内容或删除落进索引。`markResolved` 先 `add -A`，失败再 `rm -f` 兜住「文件已不在工作区」的情形。`checkout-index` 补进 `INDEX_ONLY_WRITES`，否则会被当作历史写操作白作废提交图窗口。

**冲突未解决时禁止提交。** 与 VS Code 的 action button 同一判据：存在未解决冲突时提交按钮禁用。git 本会以 `not possible because you have unmerged files` 拒绝，提前禁用并把原因写进提示行比让它失败更清楚。

## Alternatives considered

**解析 `git diff --cc` 的三路输出。** 否决：`@@@` 头与双列前缀要另写一套解析与行号映射，还要改 forge 的渲染契约；`git diff HEAD` 已经给出普通两路 hunk，冲突标记作为新增行天然可见。

**只排除 `U` 码，不加第三分组。** 否决：冲突条目仍需一组解决动作，混在「更改」组里会让暂存与丢弃按钮出现在对它们无效的行上。

**用 `git checkout --ours/--theirs` 承担采用一侧。** 否决：该侧缺失时整条命令失败，且「我方删除」这类冲突下用户要的其实是「保留对方」，一条命令表达不了。

**复用 forge 的 `DiffFile` 显示冲突。** 否决：`DiffFile` 显示的是「同一文件的两侧」按 `@@` 分块，配套的动作只能整文件生效；冲突的实际粒度是「这一段取哪边」。

**按 `<<<<<<<` 标记切段。** 否决：标记是 git 写在工作区里的中间产物，用户手工改过之后与真实三方内容不再对应，切出来的段会错位；`:1:`/`:2:`/`:3:` 才是 git 记录的三份权威内容。

**引入完整的合并编辑器（可编辑结果、view zone、滚动同步）。** 否决：那需要一套带编辑状态的组件；这里用只读的三列加逐段覆盖，读的是同一模型，覆盖同一个决策而实现量小得多。

**在合并视图里提供并集、基线、两边都丢弃。** 否决：视图的职责是判断「这一段该信谁」并据此给编辑指导，不是产出最终文件；选项一多，逐段判断就退化成一排按钮的排列组合。

**给冲突条目保留一个「取基线」按钮。** 否决：`:1:` 只是共同祖先，很少是用户想要的最终内容；宿主侧的取源已按种类使用它，不需要单独暴露成动作。

## Consequences

**收益**：冲突条目有了独立分组与就地解决入口；`UU` 不再重复出现；丢弃按钮不再出现在对它必然失败的行上；提交按钮的禁用理由与 git 的拒绝理由一致。差异页可按段逐处取一侧，同一文件的不同段落互不影响；普通文件也能按块暂存与取消暂存。

**代价**：

- `fileDiffContent` 多一次 `ls-files -u` 与一次 `status` 探测；分段条多一次 `git diff` 取块。都是只读，且仅在打开差异页时发生。
- 合并视图不显示差异行号与代码高亮：它画的是三方真实内容块，不是统一的 `@@` 差异。
- 只有两个覆盖方向，因此想「两边都留」或「两边都丢」时只能靠改完再写回，或直接在编辑器里处理。
- 评论正文的提交走对话输入框；关闭输入框或切换会话时未提交的评论正文丢失。
- 取舍只存在页面状态里：刷新或切走会丢失选择，需要重新选；结果不随选随写，必须点「写回结果」。
- 写回直接覆盖工作区文件，没有撤销栈；写坏之后只能重做取舍或重新执行 `git checkout -m`。
- 分段暂存按块而非按行：块由 git 的 `--unified=3` 上下文决定，同一块里相邻的两处改动无法只取其一。
- 「采用我方」把该阶段内容写进索引即视为已解决；用户在差异页上看到的仍是解决前的快照，需要重取本页才能看到结果。
- 关闭自动刷新时，在差异页解决冲突后变更区不会自动更新，需要手动刷新。

## Testing

- `test/conflict-entry.test.mjs`：七种 XY 到种类的映射、分组白名单（冲突不进另外两组）、动作可用性矩阵、冲突标记检测、已暂存计数排除未合并条目。
- `test/api-conflict.test.mjs`：经真实路由与临时仓库构造 `UU`/`AA`/`DU`/`UD`，断言差异有 hunk 且新侧含冲突标记、阶段取值、五种动作的结局、已解决路径与缺失阶段的报错、单条失败不影响同批；另有一条负向用例证明 `git restore` 与 `show :<path>` 对未合并路径都会失败，因此丢弃不能复用。
- `test/merge-ranges.test.mjs`：行差异（替换、纯插入、纯删除、相隔较远各自成段）、区间对齐（双方改同一处成为冲突、单侧改动不算冲突）、取舍与结果拼装、未处理区间保留基线、双方新增同一文件。
- `test/forge-adapter.test.mjs`：jsdom 里渲染合并视图——两个覆盖方向（`《`/`》`）、已选择后标为已处理、三方一致时给无改动说明、选中行后浮出评论框并注明该侧行号；评论定位文本写明「我方 / 对方第几行」。
- `test/status-snapshot.test.mjs`、`test/submit-state.test.mjs`、`test/forge-adapter.test.mjs`：分别为未合并标记、冲突未解决时不可提交、forge 适配层的纯映射与渲染。
